## TECHNICAL FIELD

[0001] The present disclosure relates to computer-implemented assistance systems. More particularly, it relates to systems and methods that observe the display of a user device while the user operates a target application, generate one instruction at a time for the user to perform, verify from a later captured display frame that each instructed step was performed before advancing, protect sensitive information by redacting or tokenizing it on the user device before any content is transmitted to a remote machine-learning model, govern that protection and the model's instructions per organization, clarify the task with questions whose options are derived from the captured frame, reuse de-identified workflow templates distilled from completed guided sessions, plan a large goal as a map of tasks whose step-level instructions are expanded only when each task becomes actionable, and tolerate transient unreadable frames in a continuously sampled guidance loop.

## BACKGROUND

[0002] Users of software routinely need to accomplish tasks in applications they do not fully know: configuring a cloud resource, reconciling a spreadsheet, completing a regulated form, running a sequence of commands, or operating an enterprise system. Help for such tasks is commonly provided by static documentation, by pre-authored walkthroughs that are injected into a particular web application, or by conversational assistants that answer questions without observing what the user sees.

[0003] Pre-authored walkthroughs and tutorials are written against one version of one application. When the interface the user is working in differs from the interface the tutorial was written for, because a control has been renamed, moved, or removed, or because a prerequisite state has not yet been established, the user must reconcile the mismatch unaided. Assistants that answer questions from a text description cannot determine where the user actually is in a task or whether an instruction was carried out.

[0004] A separate class of systems, including robotic process automation and autonomous agents, captures the user interface and then performs actions on the user's behalf by synthesizing pointer and keyboard events. In regulated or security-sensitive environments such systems raise concerns: a component with the ability to change the state of the user's systems may make unintended changes, is difficult to audit, and shifts accountability away from the human operator. When such a system predicts a wrong action, the system itself executes the error.

[0005] Any assistant that transmits a screenshot or a prompt to a remotely hosted model exposes the content of the screen or prompt to the model provider. That content may include personal data, protected health information, credentials, keys, payment card or account numbers, and internal host names. Known mitigations include masking fields within the assistant's own application, which cannot protect content shown by a third-party application; removing sensitive data irreversibly, so that the response loses the values the user needs; and masking at an organizational gateway or server after the data has already left the user device.

[0006] Organizations further lack a single mechanism that governs, per tenant, what their members' devices may transmit, whether captured frames may be retained, and what an assistant is permitted to instruct, with enforcement on the device and an audit record that does not itself store the sensitive values it reports on.

[0007] Finally, assistance systems that plan a task from a stated goal frequently need information that the user did not state. Asking too many questions delays the task; guessing produces wrong plans. Systems that learn from prior tasks commonly do so by retraining a model, which is costly and cannot be scoped to one organization's private work.

[0008] There is therefore a need for a guidance system that works with any target application, that confirms from the captured display that each instructed step was performed before advancing, that never acts on the user's behalf, that removes or tokenizes sensitive data on the device before transmission while still presenting complete answers to the user, that lets an organization govern data egress, frame retention and permitted instructions from one policy with on-device enforcement, that asks only the clarifying questions whose answers are not visible on the screen, and that reuses proven workflows without retraining. There is a further need, for goals too large to be one workflow, to plan the whole effort once as an ordered set of verifiable tasks while deferring the step-level instructions of each task until the task is actually reached, so that later tasks are planned with what was learned during earlier ones and against the interface as it then is, and to decide deterministically whether a model-generated decomposition is a genuine multi-task effort at all. Finally, a system that samples the display repeatedly while a human performs a non-instant action must distinguish a frame that is momentarily unreadable because the display is in transition from a model that has failed, so that a stronger and more costly model is not invoked on display noise.

## DETAILED DESCRIPTION

### Overview and terminology

[0025] The following description refers to the accompanying drawings. Reference numerals are consistent across figures. The term "target application 190" refers to any software with which the user is interacting on the user device, including native desktop applications, web applications in a browser, terminals and, in a mobile embodiment, a physical screen viewed through a camera. The target application is not modified, instrumented or required to cooperate. The term "guidance client 120" refers to the software component of the present disclosure executing on the user device 110. The term "frame" refers to a captured image of some or all of the display 112, or a camera image of a screen. The term "navigation record" refers to the structured output described with reference to FIG. 2. The term "read-only" means that the guidance client 120 is configured so that it does not inject pointer events, keyboard events, commands, form submissions, messages or any other input into the target application 190 or the operating system on the user's behalf; every state change in the target application is performed by the human user. The term "tenant" refers to an organization whose member users are governed by a common policy. The term "holder" refers to the account scope, tenant or individual, that owns a stored artifact.

### System architecture (FIG. 1)

[0026] Referring to FIG. 1, a system 100 comprises a user device 110 having a display 112, an input device 116 such as a keyboard, pointer or touch surface, a screen-capture interface 114 provided by the operating system or browser (for example a display-media interface in a browser, a desktop capturer in a desktop shell, or a camera on a mobile device), and a target application 190 rendered on the display 112.

[0027] The guidance client 120 executes on the user device 110 and comprises: a capture module 122 that obtains frames from the screen-capture interface 114; an on-device redaction engine 124 described with reference to FIG. 3; a token map 126 stored only in volatile memory of the user device 110; a policy-enforcement module 128 that holds the effective egress policy for the user (FIG. 5) and gates every outbound transmission; a local rehydration module 130 that substitutes real values back into model responses; a presentation layer 132 that displays instructions, flags and observations to the user, in one embodiment as a floating overlay 134 described with reference to FIG. 8; and a clarification card 136 described with reference to FIG. 7.

[0028] In one embodiment the capture module 122 computes a low-resolution signature of each captured frame, for example a small grayscale thumbnail, compares it with the signature of the previously processed frame, and arms a pending read when the signatures differ. A frame is transmitted only after the display has settled, that is, after the signature has been unchanged for a settle interval, with a forced transmission after a maximum interval of continuous change and a periodic heartbeat transmission that catches changes below the signature threshold. A random jitter is added to transmission timing. An idle display therefore causes no transmission.

[0029] The guidance client 120 communicates over a network 140 with a guidance server 150. The guidance server 150 comprises a planning module 152; a navigation and verification module 154; a server-side policy re-enforcement module 155 that re-applies the same policy engine as a second line of defense; an append-only audit log 156; a clarification handler 157 (FIG. 7); an evidence store 158 holding redacted milestone frames and reports encrypted at rest, for example with an authenticated symmetric cipher and a managed key; a policy store 160 holding egress policy objects per tenant and per user; a security gate 162 that deterministically checks commands and code before they are shown to the user (FIG. 9); an instruction-shaping rule set 164 compiled from the policy object (FIG. 5); a workflow template store 166; and a template distiller and matcher 168 (FIG. 6).

[0030] The guidance server 150 invokes one or more model services 170, comprising at least a first machine-learning model 172 having image-understanding capability and relatively low latency, used for per-frame navigation, and optionally a second, stronger model 174 used for planning and for escalation when the output of the first model is unusable. The model services 170 may be hosted by a third party and accessed with credentials belonging to the operator of the guidance server or, in a bring-your-own-key embodiment, with credentials belonging to the tenant. A tenant administration console 180 allows an administrator of a tenant to author and arm the egress policy described with reference to FIG. 5 and to retrieve session reports and audit logs for members of that tenant only.

[0031] It will be understood that the division of functions between the guidance client 120 and the guidance server 150 may vary. In every embodiment the redaction engine 124, the token map 126, the policy-enforcement module 128 and the rehydration module 130 are located on the user device 110, because their purpose is to ensure that raw sensitive values never leave the device. The planning module 152 and the navigation module 154 may alternatively execute on the device when a suitable model is available locally.

### Plan generation with planner-generated visible-when-done conditions

[0032] When a user states a goal (for example "create a virtual network with a public and a private subnet in region X", "reconcile this bank statement against the ledger", or "configure single sign-on for this tenant"), the guidance client 120 transmits the goal, after on-device cleaning by the policy-enforcement module 128 and optionally with an initial redacted frame, to the planning module 152. The planning module 152 may first conduct a short scoping interview comprising a small set of goal-specific questions whose answers are folded into the plan, may retrieve current reference material (for example by reading a link named in the goal), and may incorporate user-provided reference documents which, in a desktop embodiment, are extracted and governed entirely on the device and used for that plan only.

[0033] The planning module 152 prompts the planning model 174 to return an ordered list of steps, each step being a data record comprising: a short action text; a visible-when-done condition, that is, the specific display content that will be visible once the step is truly done, expressed as display content rather than as an element locator or script; optionally an official page to open; an array of exact commands to type, with real values filled in; and a file path with exact file content where code is to be written. The visible-when-done condition is generated by the planning model together with the plan, so that each step carries the postcondition against which the same model family will later judge the step. In one embodiment the plan is grounded by a method anchor selected from a catalog of canonical methodologies keyed to the goal's field, so that steps follow the standard professional method for that field.

[0034] Each returned step is passed through the security gate 162, which deterministically matches commands and code against a catalog of destructive-operation patterns (for example recursive deletion, dropping a database, force-pushing over history, infrastructure teardown, disk formatting), sets a destructive indicator with a human-readable reason, and checks dependency versions named in code against a vulnerability database, annotating known-vulnerable versions with the safe fix. When the vulnerability database is unreachable the gate reports that fact rather than passing silently. The display gating of a destructive step is described with reference to FIG. 9.

[0035] In some embodiments, before the planning model is invoked, the template matcher 168 is consulted (FIG. 6). When a stored workflow template is classified into the serving tier, the plan is produced by adapting that template rather than by a full planning pass; when a template is classified into the seeding tier, the template is supplied to the planning model as context; otherwise the planning model plans without a template.

### The observe, instruct, verify, correct and advance loop (FIG. 2)

[0036] Referring to FIG. 2, loop 200 begins at step 202 with receipt of the goal and at step 204 with generation of the plan as described above. At step 206 the capture module 122 captures a frame. At step 208 the redaction engine 124 produces a redacted frame on the device (FIG. 3). At step 210 the guidance client 120 transmits the redacted frame together with the cleaned goal and the entire checklist, that is, every step with its current status and its visible-when-done condition, to the navigation module 154.

[0037] At step 212 the navigation module 154 prompts the first model 172 with the redacted frame and the checklist and instructs it to read the screen and determine where the user actually is, not where the list assumes, recognizing that the user may have finished several steps, skipped one, done them out of order, or be on a screen the plan did not foresee. The model is required to return a navigation record consisting of: a completed set, being the identifiers of the steps whose visible-when-done conditions the frame shows satisfied (only steps whose completion can actually be seen); a current step, being the one step the user should do next as judged from the frame; a guidance instruction, being the next action written for this exact screen and naming the visible control (for example "Click the Create button at top right" or "In the IPv4 CIDR field type 10.0.0.0/16") or giving the exact command or code to type, limited to one action; an observation, being one sentence stating what is on screen; a flag, being the specific problem and its fix if something is wrong or risky (a wrong value, a wrong place, an error message, a paid option where a free one was wanted), otherwise empty; and a done indicator that is true only when the whole goal is complete on screen. In one embodiment the record is a structured object with fields for the completed set, the current step, the guidance, the observation, the flag and the done indicator; step numbers are converted and bounds-checked by the server before use.

[0038] At decision 214 the navigation module 154 applies the gating rule: the current step may advance only if the frame shows the visible-when-done condition of the previously instructed step, or of any later step, satisfied. If so, at step 216 the server marks those steps completed, records the time of confirmation and, if evidence retention is enabled by the governing policy, stores the already-redacted frame as that step's milestone evidence in the evidence store 158, exactly once per step. If not, at step 218 the guidance field carries the exact corrective action; where an error is visible, the model reads the error and gives the exact fix; where the model cannot see what it needs (output scrolled off, a dialog covering it, a blurry camera image), the guidance asks the user to make it visible. At step 220 any flag is surfaced prominently and is cleared automatically when a later frame shows the user back on track. The corrective instruction is derived from the same navigation record that produced the verification verdict, so that verification and correction are produced in one model call over one redacted frame.

[0039] The loop implements two further rules. First, at step 230, prerequisite re-targeting: if the current step cannot be performed yet because something earlier is absent from the screen (the project, scenario, sheet or table it needs does not exist; a required control is absent or disabled because setup is incomplete), the navigation record identifies as the current step a step that establishes the prerequisite, provides as the instruction the action that establishes it, and states in the observation what was missing. The blocked instruction is not repeated and the system does not wait for the user to become stuck. Second, at step 232, equivalent-control substitution: because the target application may have changed since the plan was generated, if the control named in a step is not visible, the navigation record provides as the instruction an action directed to a different control that is visible in the redacted frame and that performs an equivalent function, for example a renamed label, a different tab or menu, or a moved button, and at step 234 provides an indication that the target application differs from the plan. The model is instructed never to direct the user to a control that is not visible and never to repeat a stale instruction. Only when no equivalent control is visible does the record say so and direct the user to research the current interface.

[0040] The discrepancy indication produced at step 234 is used downstream. In one embodiment it is recorded in the session event log and in the session report. In some embodiments it is supplied to the planning module 152 as a re-planning signal so that the remaining steps are regenerated against the current interface, and, where the plan was served from a workflow template (FIG. 6), it triggers supersession of the template's recorded target with the control actually found.

[0041] At step 222 the presentation layer 132 displays the guidance, the observation and any flag. At step 224, shown outside the system boundary, the human user performs the action in the target application 190 using the input device 116. The guidance client 120 contains no code path that injects an input event into the target application; the only output path from the loop to the user device is the presentation layer 132. At decision 226, if the done indicator is true, the loop ends at step 228 with generation of the session report; otherwise the loop returns to step 206 for the next frame. The subsequently captured frame is thus the oracle by which the system verifies that the instructed action was performed and succeeded.

[0042] Model escalation. The navigation module 154 evaluates whether the output of the first model 172 is usable, that is, whether it contains at least a guidance instruction, a non-empty completed set, a current step, an observation, or a true done indicator. If the output is unusable, or if the first model raised an error, the same redacted frame and checklist are re-submitted to the stronger model 174 for that call only. The escalation, and any failure of the stronger model, is recorded as an event visible to the user, so that the user is never silently served a weaker result than the one configured. The model identity is kept in the server audit and operator incident log and is not shown to end users. The immediate re-submission described in this paragraph applies to a one-off read, that is, a read requested by the user or performed once for a frame outside the continuous loop. In the continuously sampled watch loop the re-submission is further gated by the transient-unreadable-frame tolerance described with reference to FIG. 13, under which a single unreadable frame does not by itself cause escalation.

[0043] Periodic self-audit. Independently of the per-frame navigation, a less frequent check submits the goal, the checklist, the recent action history and the current redacted frame and asks only whether the work is still heading at the goal or has drifted or stalled. It returns an on-track indicator, a one-sentence steer and a re-plan suggestion. It never changes the plan itself; re-planning is initiated by the user or by a clarification answer (FIG. 7) and may preserve already-confirmed steps.

[0044] On-demand channels. In addition to the continuous loop, the user may ask a question about the current screen, request the actual result of a task (a number, a table, a query or code) accompanied by a confidence indicator and a statement of how it was obtained and how to verify it, or request a composed document. All of these channels pass through the policy-enforcement module 128 before transmission. In a further embodiment a spreadsheet computation is performed entirely on the device: the file is parsed locally, only a description of the request, the column schema and the row count are transmitted, a computation specification is returned, and the specification is validated and executed locally over the full data so that the rows never leave the device.

### On-device redaction, tokenization and local reconstruction (FIG. 3)

[0045] Referring to FIG. 3, pipeline 300 is executed on the user device 110 by the redaction engine 124 and the policy-enforcement module 128. Two kinds of outbound content enter the pipeline: outbound text 302 (the goal, questions, pasted sources, document text, clarification answers) and outbound frames 304.

[0046] A detector 306 identifies sensitive spans using a catalog of rules. In one embodiment the rules include: private-key blocks; API keys, tokens and credentials by provider-specific patterns and by label (a value adjacent to a label such as password, secret, API key, access token or client secret); URLs embedding credentials; government and financial identifiers including social-security and social-insurance numbers, payment card numbers validated by checksum so that version strings are not falsely matched, international bank account numbers, and bank account and routing numbers; email addresses and telephone numbers; IPv4 and IPv6 addresses, with version strings guarded, and private or internal host names; and labeled health and personal record fields such as date of birth, medical record number, patient, member, policy and account numbers, driver-license, passport and tax identifiers, street addresses and postal codes. The detector preserves public product domains, file paths, commands and version numbers so that guidance quality is retained. The same detector implementation executes on the device and on the server, so there is no weaker path.

[0047] A policy 308, being the effective egress policy for the user (FIG. 5), supplies, per category (for example secrets, health information, personal information, intellectual property, host, email, telephone, card, national identifier, bank identifier and custom categories), an action selected from send, redact (irreversibly replace with a typed tag such as "[EMAIL]" or "[REDACTED]"), withhold, or tokenize (reversibly replace); a list of block words, being exact words or phrases such as a project code name or a client name that are always removed and never reversible; and custom patterns with their own actions. An action router 310 applies the policy to each detected span. The same policy 308 and the same detector 306 are applied to recognized text lines of frames and to outbound typed text; a single policy object therefore governs both modalities.

[0048] For a span whose action is tokenize, a token generator 312 produces a stable, typed placeholder token comprising a type indicator and an index, for example "[[EMAIL_1]]", "[[IP_2]]", "[[CARD_3]]", "[[SECRET_4]]" or "[[HOST_5]]". The token format is distinctive so that a language model preserves it verbatim, and it carries a type hint so that the model still reasons correctly about the kind of value without seeing it. The same real value is mapped to the same token within a session, so references stay coherent across turns. The token-to-value mapping is written to the token map 126 at step 314; the token map resides only in volatile memory of the user device, is never included in any request, is never written to any server log, is excluded from every transmission from the device, and is zeroed when the session ends or is reset. In one embodiment only whole-match categories, where the matched text is exactly the value, such as an email address or an IP address, are reversibly tokenized, while labeled fields are redacted irreversibly.

[0049] For outbound frames 304, the redaction engine 124 performs on-device optical character recognition 316 of the frame, for example using a recognition engine loaded into the browser or desktop shell and pre-warmed when a protected session begins so that the first frame is not delayed. For each recognized text line, the recognized text is passed through the same detector 306 and policy 308 used for typed text, including the tenant's block words and custom patterns. If any sensitive span or block word is found in a line, a line-mask step 318 paints an opaque region over the entire bounding box of that line, with a small margin, on a canvas copy of the frame; masking the whole line is tolerant of values split across words. The canvas is re-encoded, for example as a compressed image, to produce the redacted frame 320. If nothing sensitive was found the original frame is used.

[0050] Fail-safe downscaler 338. If the recognition engine cannot run on the device, for example because it failed to load or is unavailable on the platform, the redaction engine 124 does not transmit the frame at its captured resolution. Instead it produces a downscaled copy of the frame at a resolution at which text of the frame is illegible, and transmits that copy. In some embodiments the target resolution is derived from a legibility criterion: the downscale factor is chosen so that the effective height of the smallest text run estimated for the frame (for example from the last successful recognition pass, or from a default assumption about user-interface text height) falls below a threshold height in pixels, or, where a reduced-capability recognizer is available, so that an optical character recognition pass over the downscaled copy returns no text run above a confidence threshold. The recognition engine is marked unavailable so that the fail-safe is not retried on every frame, and guidance continues on the degraded frame, with the model directed to ask the user to make content visible where it cannot be read, rather than blocking the session. The fail-safe is reported to the user as a best-effort backstop rather than a guarantee.

[0051] The tokenized or redacted text 322 and the redacted frame 320 are then transmitted at step 324 to the guidance server 150 and on to the remote model 326. Before transmission the user is shown a short summary of what was removed on the device (for example "Stripped on your device before sending: 2 emails, 1 IP address"); nothing is silently dropped.

[0052] The model's response 328 contains placeholder tokens where it refers to tokenized values. The local rehydration module 130 performs rehydration 330 by substituting each placeholder token present in the token map 126 with its real value. Rehydration is applied to every string in the response structure, walking nested objects and arrays. In a streaming embodiment, a streaming buffer 340 receives each partial chunk of a streamed response as it arrives; because a placeholder token may be split across chunk boundaries, the buffer retains a tail of the received text no longer than the maximum token length, applies the substitution to the portion of the buffer that cannot contain the beginning of a token, releases that portion for display, and carries the tail into the next chunk, so that the user reads a rehydrated answer progressively while no token is missed.

[0053] A missing-token handler 332 handles the case in which a token that is present in the token map is absent from, or altered in, the response. The response is left unmodified at that location, an indication that the response is incomplete at that location is presented, and no value that is not present in the token map is substituted. The token map is not consulted approximately: an altered token that no longer matches an entry exactly is not matched to the nearest entry. The displayed answer 334 therefore names the exact real values (for example a specific patient record number) although neither the guidance server nor the model received them.

[0054] An audit entry 336 records the call, whether protection was on, the counts of what was removed by category, whether a frame was sent, and the protected text that actually left the device; the entry contains placeholders and tags, never raw values. The schema of the audit entry is described with reference to FIG. 5.

[0055] Defense in depth. The guidance server 150 applies the identical policy engine again to inbound text and, in some embodiments, to inbound frames by server-side recognition, through the re-enforcement module 155, so that a control is enforced even if the first layer is bypassed; any further removal made by the server is recorded in the audit entry as a category count. Text that is persisted for later re-use (for example a saved playbook, a learned fact, or a workflow template) is always redacted rather than tokenized, because stored text is shared and never rehydrated; the server applies a mandatory scrub floor on write and the same policy on injection into any later prompt.

### One guided step end to end (FIG. 4)

### Tenant-governed egress, instruction shaping and evidence retention (FIG. 5)

[0057] Referring to FIG. 5, arrangement 500 comprises a tenant administrator 502 who, through a policy editor 504 in the administration console 180, optionally a guided wizard seeded from compliance-framework presets and regional regimes, authors a policy object 506. The policy object comprises: per-category actions 508 selected from send, redact, withhold and tokenize; block words 510; a mode 512 selecting between redaction and tokenization; a screenshot-evidence setting 514 controlling whether redacted milestone frames may be retained in session reports and logs for the tenant's members at all; a retention window 516 after which sessions, their evidence frames and their audit records are deleted together; and an armed and locked state 518. Custom patterns with their own actions are also part of the object. The object carries a version number and the identity of the account that last changed it.

[0058] Arming the policy makes it the enforced criteria for every member of the tenant. Scope resolution 520 determines the effective policy for a user: a member of a tenant receives the tenant's armed policy and cannot edit, weaken or opt out of it (self-service policy controls are denied to members); an individual not belonging to any tenant may manage their own policy; a platform administrator may set and lock any policy. The effective policy is distributed at 522 to each member's guidance client 120, where the policy-enforcement module 128 applies it on the device, before transmission, to typed text and to screen frames alike (pipeline 300). The guidance server 150 re-applies the identical policy on receipt at 524 as a second line of defense.

[0059] Locked state and lock release 536. When the policy object is in the locked state, the policy store 160 refuses every modification request, including requests from a tenant administrator. In some embodiments a modification is accepted only through a lock-release operation 536 that requires re-authentication of an administrator whose role is hierarchically above tenant administrator (for example a platform administrator), and that writes to the audit log 156 an entry identifying the acting account, the prior policy version and the new policy version, the entry excluding every policy value that is a sensitive value. A modification request that is not accompanied by a completed lock-release operation is refused with a status that names the locked state as the reason.

[0060] Instruction-shaping rule set 534. In some embodiments the policy object 506 is compiled into a rule set 534 that is applied by the guidance server 150 to the output of the planning model and of the navigation model. The rule set comprises forbid rules and require rules derived from the per-category actions and from an organization's written security policy: a forbid rule identifies content that the model must not instruct the user to expose or perform (for example a step that would require the user to type a value of a withheld category into a third-party service, or a step that uses a protocol the organization prohibits), and a require rule identifies content that a step of a given kind must include. When a generated single-step instruction, a plan step, a result or a composed document matches a forbid rule, or omits content demanded by a require rule, the server annotates the item with a policy reason citing the originating policy document and section and presents the compliant alternative; the server does not silently rewrite or delete the model's text. In some embodiments a matching single-step instruction is replaced by a policy-reason instruction that tells the user why the step was withheld and what to do instead. The rule set 534 is versioned together with the policy object 506 from which it was compiled, so that one policy version governs the sensing side (what leaves the device), the retention side (whether a frame is kept) and the advice side (what the model may instruct). Alphanumeric rule terms are matched at word boundaries so that a rule naming one protocol does not fire on the name of a different protocol that contains it as a substring; a require rule fires only when its trigger context is present.

[0061] The screenshot-evidence setting 514 gates whether the server stores the redacted frame at step 216 of FIG. 2 into the evidence store 526 (corresponding to 158); when the setting disables retention, no frame is retained anywhere and the report contains the confirmed steps and timestamps without exhibits.

[0062] Transmission audit 530 and audit record schema 538. For each transmission from a member device, the audit log 156 receives a record whose fields are drawn from a closed schema 538 consisting of: the version of the policy object in force; the mode; a count of items removed in each category; whether a frame was transmitted; the purpose of the call; and, in some embodiments, the protected text that left the device, consisting of placeholders and typed tags. The schema has no field capable of storing a matched sensitive value, so the record cannot store one. In one embodiment each record carries a sequence number, the digest of the preceding record and its own digest, so that the integrity of the chain can be verified on download.

[0063] Retention sweep 528 and single-operation purge 540. A retention sweep 528 runs periodically and, for each session of the tenant older than the retention window 516, performs a single-operation purge 540 that removes the session record, every redacted frame stored as evidence for the session and the audit records of the session together, leaving no residual per-session data. Deleting the audit records with the session is permissible because the records exclude every sensitive value and the retained value of the audit is bounded to the session's lifetime. An administrator may retrieve any member session's report and audit log, in progress or finished, scoped strictly to their own tenant, at 532; a member-level alert naming who, which categories and counts, which task and when, never the values, is raised to the tenant administrator when a member enters sensitive data that was redacted on the device, and may be relayed to the tenant's security-event tooling.

### Screen-derived clarification (FIG. 7)

[0065] Referring to FIG. 7, flow 700 begins at 702 with a planning call that receives the goal, the scoping answers and, where available, the current redacted frame. At 704 the planning model is permitted to generate, together with the plan, at most one clarification question that it cannot answer from the frame and that is essential to planning. The question comprises a kind (choice or free text) and, for a choice question, a shortlist of between two and five options that the model infers from the content of the captured frame and the task context, for example the named environments, projects, accounts or regions that are visible on screen. The prompt rule directs the model to treat the options as a best-guess shortlist that never closes the option space.

[0066] At 706 a suppression check applies: when the answer is determinable from the captured frame, the model does not ask. In one embodiment the rule is expressed as an instruction that the model must read the answer off the screen when it is there rather than asking for it; in some embodiments the server additionally discards a returned question whose answer text appears in the recognized lines of the frame.

[0067] At 708 the clarification card 136 presents the question with the options 710 as selectable chips, a free-text entry 712 that is always available so that the user may give an answer that is not in the shortlist, and a skip control 714. A question with fewer than two valid options is converted to a free-text question or discarded.

[0068] At 716 the answer is stored in a session scope, being a record of question and answer pairs that persists for the session and is supplied to every subsequent planning or re-planning call. When the user skips, at 726 a record is stored that the question was skipped and that planning is to proceed on a stated best assumption and to confirm with the user before any irreversible action; the assumption is shown to the user.

[0069] At 718 the client issues a plan regeneration request that carries a clarification-origin indicator. At 720 the guidance server 150 distinguishes a regeneration that carries the indicator from a user-initiated re-plan: a user-initiated re-plan is checked against, and decremented from, a per-task regeneration limit before any model call is made, whereas a regeneration carrying the clarification-origin indicator bypasses the limit check and does not decrement the counter. The regenerated plan 722 incorporates the answer or the assumption. The technical effect is that the answer to a question the system itself asked does not consume the user's allowance for correcting the system, and the regeneration reuses the already stored scope without a further model call to re-derive it.

[0070] At 724 an answered or skipped question can be reopened from the card: the stored answer is removed from the session scope and the question is presented again; a re-answer triggers a further regeneration that again carries the clarification-origin indicator.

[0071] In some embodiments the clarification handler 157 consults the matched workflow template of FIG. 6: when the environment record of a template that is classified into the serving or seeding tier for the same holder already contains the answer to a scoping or clarification question (for example the jurisdiction or the software in use), the question is pre-filled or omitted and only attributes that are absent from, or contradicted by, the environment record are asked.

### Workflow-template capture and tiered retrieval (FIG. 6)

[0072] Referring to FIG. 6, arrangement 600 is described as an embodiment that improves planning by retrieval rather than by model training, and that keeps one holder's work private to that holder.

[0073] Capture. On completion of a guided session, a completed session record 602 comprising the goal, the scoping answers, the ordered steps with their statuses and the event log is evaluated at 604 by a clean-success predicate. The predicate is satisfied only when the session has at least one step, every step carries a done status that was confirmed from the screen by the navigation record or by the user, and the final event of the session is not an unresolved flag. A session that fails the predicate yields no template.

[0074] When the predicate is satisfied, a distiller 606 deterministically, without any model call, generates a workflow template 608 comprising: a goal signature 610, being an ordered token set produced from the goal text by lowercasing, removing email addresses, URLs and possessives, removing tokens that are purely numeric or version-like (so that volatile specifics such as years, counts and version numbers do not enter the signature), removing stop words, applying light singularization and removing duplicates; a normalized application key 612 and, where known, an application version; an environment record 614 derived from the scoping and clarification answers, comprising a jurisdiction, a list of named software, a manual-versus-software indicator and the question-and-answer conventions of the session; ordered steps 616 each with the step text, its visible-when-done condition, a step kind selected from command, code, navigate and user-interface action, any exact command or code, and the first on-screen target named in the guidance for that step; and a success signal 618, being the visible-when-done condition of the last step.

[0075] De-identification is applied in two layers. At 620 a pre-scrub removes email addresses and long digit runs from prose fields of the template, while command and code content is exempt from the pre-scrub so that exact commands are preserved. At 622, at persistence, every string value of the template is passed through the policy-aware stored-text scrub of the holder (the same chokepoint used for every persisted text, see paragraph [0055]), which removes or replaces sensitive values under the stored policy, applies a full scrub when no policy is present, and preserves the keys of the template. Depth, length and collection-size caps bound the scrub.

[0076] Storage. The template is written to a holder-scoped store 624. For a user belonging to a tenant, the store is that tenant's private template store 626, shared among the tenant's users and never readable by another tenant. For a user not belonging to any tenant, the store is a shared de-identified store 628 to which the user consented at registration. A tenant-level switch disables capture into, and retrieval from, the store together, so that disabling learning never leaves a silent retrieval path. A re-capture whose normalized goal signature and application key equal those of an existing template supersedes that template in place, incrementing its version and serve count and retaining exactly one prior version that is never nested. Templates carry a freshness time that is refreshed when served; a template unused for an expiry interval is removed, and each holder's store is capped with eviction of the least-fresh template.

[0077] Retrieval. For a new goal 630 from a requesting user, the matcher 168 computes at 632 the goal signature of the new goal and, for each template in the requesting user's holder store, computes at 634 three scores: a goal similarity, being the mean of the Jaccard index and the overlap coefficient of the two signature token sets; an application similarity, which treats two normalized application keys as matching when they are equal or when one is a token subset of the other after removal of generic interface words; and an environment compatibility score, which is reduced by each contradiction between the new session's environment and the template's environment record, where a contradiction is a differing jurisdiction, a disjoint software list, or a conflict between manual and software performance, and where an attribute absent from the new session's environment never contradicts. A weighted combination of the three scores is formed with named weights (in one embodiment 0.6, 0.25 and 0.15).

[0078] At 636 a tier gate classifies the best candidate. The candidate is placed in the serving tier 638 only when all of the following hold: the weighted combination meets a first floor (in one embodiment 0.75); the application keys match; no environment attribute contradicts; and the environment compatibility score meets an environment floor (in one embodiment 0.5). The candidate is placed in the seeding tier 640 when the weighted combination meets a second, lower floor (in one embodiment 0.45) and it was not placed in the serving tier. Otherwise the candidate is withheld at 642 and no template is used; a near miss is never force-fitted. All floors and weights are named constants, so the classification is explainable and auditable.

[0079] A serving-tier template is served at 644 through a single adaptation pass in which the model is asked only to adjust the template's steps for the differences between the template's environment record and the new session's environment (for example a changed version or jurisdiction), rather than to plan from nothing. In one implementation the adaptation pass takes the form of supplying the serving-tier template to the planning model together with a directive to follow the template as the backbone of the plan and to adapt it only where the current environment or the current frame differs; a seeding-tier template is supplied with a directive to treat it as a similar proven workflow to adapt. In that implementation each serve is counted on the template so that a template's usefulness is observable, and the capture of paragraphs [0073] to [0076] runs at the end of every guided session, so that the store grows from use without any separate curation step. A seeding-tier template is supplied at 646 to the planning model as context for a full planning pass. In either case the resulting plan is still live-verified step by step against the real screen by loop 200; a served workflow is never replayed blindly. At 648 the environment record of the matched template pre-fills the clarification and scoping questions as described in paragraph [0071].

[0080] Drift-triggered supersede 650. In some embodiments, when during live verification of a served template the navigation record reports, by way of the discrepancy indication of step 234, that the on-screen control differs from the first on-screen target recorded for that step in the template, the template's steps are replaced with the corrected steps after the session completes cleanly, the template's identifier and serve count are preserved, and exactly one prior version is retained. The template thereby heals from interface drift observed in use.

[0081] In some embodiments a template is permission-aware: a step requiring a permission that the requesting user lacks is omitted or flagged when the template is served to that user. In some embodiments templates are additionally projected into a vector index of the holder for semantic recall.

### Model routing and reliability

[0087] The guidance server 150 routes to the highest-ranked model reachable with the credentials in effect for the user, being the operator's platform credentials or the tenant's own credentials, with a reliability ladder: a retired or rate-limited model is replaced by another current model on the same credentials, then, in platform-credential mode only, by the next provider; a tenant's own credentials are never silently replaced by the operator's, and a frame belonging to a tenant pinned to its own credentials is never routed to platform credentials. ### Multi-task project guidance (FIG. 10)

[0090] The loop of FIG. 2 guides one task, that is, one workflow that a person completes on its own, from a single ordered plan of steps. Many goals are larger than one workflow: rolling out a service-management platform, migrating a tenant to a new identity provider, or standing up a regulated environment each comprise several distinct workflows that must be done in an order, that depend on one another, and that together must reach a stated end. Planning such a goal as one flat list of steps fails in two ways. The list is generated before any of the work is done, so the later steps are planned against an interface, a set of names and a set of facts that the earlier work will change; and the list is too long for a human performer to hold, so the performer loses the sense of where the effort stands. Referring to FIG. 10, a project engine arrangement 1000 addresses both failures by planning in two tiers and expanding the lower tier only when it is needed.

[0091] A project goal 1002 stated by the user is transmitted, after on-device cleaning by the policy-enforcement module 128, to a map planner 1004 of the planning module 152. The map planner 1004 prompts the planning model 174 once, at the level of workstreams rather than clicks, to return a project map 1006 comprising an ordered plurality of task descriptors 1008 and a project end-state 1016. Each task descriptor 1008 comprises a task goal 1010, being one sentence stating what that task achieves; a done-state 1012, being a statement of display content that will be visible when the task is complete; and a set of dependencies 1014, being references to the earlier task descriptors that must be in a done state before this task can begin, which may be empty. The project end-state 1016 comprises one sentence stating what is true when the whole project is complete and a short list of concrete checks that must all hold at the end. The map planner is instructed that one workflow is one task, that the task descriptors must together reach the end-state with no gap and nothing extra, that a goal which is in truth a single workflow is to be returned as exactly one task rather than padded into several, and that no step-level instruction is to be produced at this tier. The project map 1006 therefore contains no instruction to click, type or run anything; it contains only what each task achieves, how its completion will be visible, and what it depends on. The map planner may also return a short project name, and may decline a goal it must not help with, in which case no project is created.

[0092] Before the project map 1006 is persisted, a breakdown gate 1018, described with reference to FIG. 11, decides deterministically and without any model call whether the decomposition is a genuine multi-task effort of real, distinct, verifiable tasks. A map that fails the gate is not persisted; the user is returned to single-task guidance with a suggested goal, which in one embodiment is the task goal of the first returned task descriptor. A map that passes is written to a project store 1020 together with an initially empty forward-learnings ledger 1026 described in paragraph [0095]. Dependencies returned by the planner as positions in the returned list are remapped to the persistent identifiers of the stored task descriptors at this time. Each task descriptor is stored with a state selected from pending, active, done and rerun, with an order, with a flag recording whether its steps have been expanded, with a reference to the guided session that expands it, and with fields for its outcome and telemetry; the allowed state transitions are pending to active, active to done or back to pending, done to rerun, and rerun to active or done, and a transition outside this set is refused. The project's own state is derived from its task descriptors rather than stored independently: planning while no task has left the pending state, active once any has, and done when every task descriptor is done.

[0093] A next-task selector 1022 selects, from the project map, the task descriptor to guide next. The selector considers the task descriptors in the pending state in their stored order and returns the lowest-ordered one whose dependencies 1014 are each in the done state. The selector also computes the set of every pending task descriptor whose dependencies are all done, so that the presentation layer 132 can offer the user both the recommended next task and any other independent task that is ready now; the user may pick any ready task, but never one whose dependencies are unmet. When no pending task descriptor has its dependencies met, the selector returns nothing, which is the case either when every task is done or when the remaining tasks are blocked on one that is in progress.

[0094] A just-in-time expander 1024 generates the steps of the selected task, and only of the selected task, when the task becomes actionable and not before. The expander invokes the planning module 152 for the task goal 1010 of the selected task descriptor as the goal of an ordinary single-task plan, so that the result is an ordered plan of steps of the kind described in paragraph [0033], each step carrying its planner-generated visible-when-done condition, each passed through the security gate 162, and each eligible for the template matcher 168 of FIG. 6. The expander supplies the planning model, in addition to the task goal, with the contents of the forward-learnings ledger 1026 under a directive to treat them as current, verified facts that take precedence over the model's own prior knowledge. The resulting plan is written into a new guided session 1028 that is linked to the task descriptor, the task descriptor is marked expanded and moved to the active state, and the guided session 1028 then runs as the loop 200 of FIG. 2 in every respect: frames are captured and redacted on the device, one instruction is presented at a time, no input is injected, and each step advances only when a later redacted frame shows its visible-when-done condition satisfied. In one embodiment the done-state 1012 of the task descriptor is supplied to the guided session as the task-level verification target, so that the navigation module 154 reports the task done only when a redacted frame shows the done-state satisfied, in addition to the per-step visible-when-done conditions; in another embodiment the task is treated as complete when the guided session is finalized with its steps confirmed, and the done-state 1012 is carried into the project report of paragraph [0098] as the statement against which the task's outcome is read. Because expansion is deferred, the steps of task N are planned against the interface as it exists after tasks one to N minus one have been performed, and the performer is shown one task's worth of steps at a time.

[0095] The forward-learnings ledger 1026 is a project-scoped, ordered list of generalized facts, each stored with the task descriptor that was its source. Two write paths feed it, shown together as ledger write-back 1032. First, when the expander 1024 plans a task, the planning model is asked to flag, in one line, any generalized learning it formed about the tool or flow in use that differs from older knowledge (for example that an export control has moved under a settings menu in the current version); such a learning is appended at that time so that it is available to the very next expansion. Second, when a task reaches completion as described in paragraph [0096], facts confirmed during its guided session, in some embodiments including the discrepancy indication of step 234 that records where a named control was actually found, are appended. Every append is deduplicated by a normalized comparison of the fact text, so that a fact learned twice is stored once; the ledger is bounded to a fixed number of most recent entries so that it cannot grow without limit; and an empty fact is ignored. The ledger is distinct from the workflow templates of FIG. 6 in scope and in lifetime: a template is distilled from a whole completed session, is held by a tenant or by the shared store, and is matched to other users' later goals, whereas the ledger holds facts within one project for the benefit of that project's own later tasks and ends with the project. Text written to the ledger passes through the same stored-text scrub as every other persisted text (paragraph [0055]).

[0096] Task completion 1030 closes the loop for one task. When the guided session 1028 that expands a task descriptor is finalized, the project engine locates the task descriptor by its session reference, marks it done if its state permits that transition, records on the task descriptor an outcome comprising at least the number of steps whose visible-when-done conditions were identified as satisfied, the total number of steps and the session summary, records telemetry describing how the task was planned and guided (for example whether a critique pass or a stronger model was used and how long the task took), and performs the ledger write-back 1032. Marking the task done makes its dependents eligible in the next-task selector 1022, so the user is immediately shown the next actionable task or the set of tasks that are ready. A task whose session ends without every step confirmed is not marked done; it stays active and can be resumed or returned to pending, and a done task may be moved to the rerun state and expanded again, which produces a fresh plan from the ledger as it then stands.

[0097] A project completion check 1034 declares the project complete only when every task descriptor is in the done state. In the embodiment in which the done-state 1012 is supplied to the guided session as a verification target, the project end-state 1016 is additionally verified: the final redacted frame of the last task, or a frame captured on request, is submitted with the end-state checks to the navigation module 154, and the project is declared complete only when the frame shows the end-state satisfied; otherwise the unmet checks are reported and the user may inject a task (FIG. 12) to meet them. The project engine never marks a task or a project done on the strength of the plan alone; the state of the display, as read from redacted frames, remains the oracle at both tiers.

[0098] A project report generator 1036 produces, on demand, a report that aggregates the guided sessions of all task descriptors of a project. In a success report, for each task descriptor in the done state, the generator lists the task's done-state 1012, its recorded outcome, and the steps of its guided session whose visible-when-done conditions were identified as satisfied, each with the condition that confirmed it, and rolls these up under the project end-state 1016 and its checks; steps not confirmed and tasks not done are listed by name and state only, consistent with paragraph [0085]. In a security report, the generator lists, per task, the steps annotated by the security gate 162 as destructive together with their reasons, and every flag raised during the task's guided session. In an issues report, the generator lists the task descriptors not in the done state with their states and the flags recorded for them. The generator is a pure aggregation over stored artifacts and makes no model call; the report is rendered in the same style as the session report of paragraph [0085] and is subject to the same screenshot-evidence setting 514 and encryption at rest.

[0099] Mid-project injection 1038, described with reference to FIG. 12, allows a request that arises while a task is active to be added to the project map without creating a duplicate task and without breaking the dependency order. It is the task-tier counterpart of the step-tier prerequisite re-targeting of step 230.

[0100] Guidance depth. In some embodiments the project engine is reachable only at a deep guidance depth, while a standard depth provides single-task guidance alone, and a depth resolver 1040 resolves the effective depth for a user from a single rule set. For an individual user the depth follows the user's subscription tier. For a member of a tenant, a platform operator sets a per-tenant ceiling, a tenant administrator assigns a depth to each seat pool of the tenant, and the resolver clamps the pool assignment to the ceiling, so that a tenant administrator can distribute depth within the operator's grant but can never grant beyond it; a pool with no assignment receives the ceiling itself. The deep depth also removes a cap on the number of tasks a user may have open at once. A user below the deep depth who states a goal that is in truth a project is shown a choice to upgrade or to shorten the goal to a single task that can start now, never a project. The resolver is a pure function of the tier, membership, ceiling and pool depth, which makes the entitlement decision reproducible and auditable.

[0101] Deepened planning. In some embodiments the plan of steps generated by the planning module 152, for a single task or for a task expanded by the expander 1024, is hardened by a second, text-only critique pass 1042 that runs when the goal is judged to branch or to be capable of failing (for example a cross-system handoff, a verification, a sign-in, an install or a configuration). The critique pass receives the draft plan and is asked to add the missing prerequisite, the on-screen fork, the recovery for a step that can fail, a value the user may not have, and any loop. Its output replaces the draft only under a monotone no-degrade acceptance rule: the hardened plan must be a real plan that is not a refusal and that contains at least as many steps as the draft; otherwise the draft is kept. Whether the critique pass ran and whether its output was accepted are recorded as telemetry on the session and, for a project task, on the task descriptor, separately from whether a stronger model was used, so that the operator can see that deep planning actually happened. The critique pass is skipped for a plain linear task, so that it adds no cost where it adds no value.

### Deterministic breakdown gate (FIG. 11)

[0102] Referring to FIG. 11, the breakdown gate 1100 (corresponding to 1018) receives at 1102 the proposed breakdown returned by the map planner 1004, being the task descriptors and the project end-state, and decides without invoking any machine-learning model whether it may become a project. The gate embodies a policy: a task is one verifiable workflow; a task whose completion cannot be confirmed from the display is not a task; and a plan cannot be padded into a project by filler or by restatement. Every check is run in full rather than short-circuited, so that the caller is shown every problem at once.

[0103] At 1104 a real-task test is applied to each task descriptor: a descriptor is real only when it has an aim, being a non-empty task goal or title, and a non-empty done-state 1012. Both are required; a descriptor with an aim but no done-state is a filler, and a descriptor with a done-state but no aim is not a task. At 1106 the identifying label of each descriptor, being its task goal or, failing that, its title, is normalized by lowercasing, trimming and collapsing internal whitespace, and descriptors whose normalized labels are equal are collapsed to one for counting, so that two restatements of the same work cannot count twice. At decision 1108 the gate requires at least two distinct real task descriptors; when fewer remain, the breakdown is, at 1110, returned to the user as a single task with a suggested goal, because one workflow is one task and never a project. At 1112 every dependency reference must resolve to a task descriptor in the set; at 1114 the dependency graph must be acyclic, which the gate determines by a three-color depth-first search that reports the members of any cycle, including a self-dependency; and at 1116 the project end-state must be defined, that is, its done sentence must be non-empty, because a project whose completion is undefined cannot be confirmed. Any failing check is an error, and at 1118 the gate rejects the breakdown with every error named; the breakdown is not persisted and the map planner is not re-run automatically. When no error is found the breakdown is accepted at 1120 and persisted as described in paragraph [0092]. A missing project goal text is a warning only.

[0104] The gate is deliberately asymmetric. Over-splitting, that is, presenting a single workflow or a padded list as a project, is an error that the gate refuses. Under-splitting, that is, a single task whose expanded plan carries more steps than a threshold (in one embodiment twenty), produces at 1122 an advisory indication only, which prompts the user or the planner to reconsider whether the task is a project; the gate never divides a task automatically, because a long linear procedure is legitimately one task and an automatic division would manufacture exactly the false project the gate exists to prevent. The thresholds and the normalization are fixed, named rules, so the gate's verdict is explainable and reproducible.

### Mid-project task injection (FIG. 12)

[0105] Referring to FIG. 12, the injection flow 1200 (corresponding to 1038) begins at 1202 when a further request from the user arrives while a task of the project is active, for example "we also need to enable audit logging". The semantic question of whether the request is the same work as a planned task is answered deterministically. At 1204 the request and the task goal and title of each task descriptor are each reduced to a set of normalized word tokens, by lowercasing, replacing punctuation by spaces and splitting on whitespace, and a token-set similarity, in one embodiment the Jaccard index of the two sets, is computed between the request and the better of each descriptor's goal and title. An empty token set on either side yields zero similarity. At decision 1206 the best-matching descriptor is compared with a threshold (in one embodiment 0.6). When the threshold is met, at 1208 the request is folded into the existing task descriptor and no new descriptor is created, so that a mid-project request cannot pad the project with a duplicate; the user is told which planned task already covers the request.

[0106] When no descriptor meets the threshold, a new task descriptor 1210 is created from the request and a placement selector 1212 decides where it belongs in the ordered map, according to what the request says about its relation to the planned tasks. When the request names a task that it blocks, that is, the new task is a prerequisite of a named task, placement 1214 inserts the new descriptor immediately before the named task, adds the new descriptor to the named task's dependencies so that the named task now waits for it, and carries the named task's own upstream dependencies over to the new descriptor so that the prerequisite still runs after them; a dependency that would reference the new descriptor itself or the named task is never carried. When the request names tasks on which it depends, placement 1216 inserts the new descriptor immediately after the latest of those tasks in the stored order and records those tasks as its dependencies. When the request names neither, placement 1218 appends the new descriptor at the frontier, being the position after the last task descriptor that is not in the done state, or at the end when every task is done. A named task that does not exist in the map is treated as unnamed and the request is appended at the frontier with a notice.

[0107] Every placement is probed for cycles at 1220 before it is committed: the dependency graph that would result from the proposed edges is walked by depth-first search. When the proposed edges would close a cycle, the flow does not refuse the user's request; at 1222 the offending edge (the edge from the named task to the new descriptor, or the requested dependency) is dropped, the new descriptor keeps only those of its originally requested dependencies that are themselves acyclic, the descriptor is appended at the frontier, and a cycle-avoided notice naming the omitted dependency is recorded and shown, so that the user knows the ordering constraint was not applied and why. At 1224 the task orders are renumbered to a clean consecutive sequence from one and the new map is persisted. The flow never mutates the stored map in place while deciding: it works on a copy and commits the result, so a rejected placement leaves the project unchanged. A task injected mid-project carries no done-state until it is expanded, and its expansion by the expander 1024 proceeds exactly as for a planned task, seeded from the ledger as it then stands.

### Transient-unreadable-frame tolerance in the watch loop (FIG. 13)

[0108] Referring to FIG. 13, the tolerance 1300 qualifies the model escalation of paragraph [0042] for the continuously sampled watch loop. In the watch loop the capture module 122 transmits a frame whenever the display settles after a change (paragraph [0028]), so that while the user performs a non-instant action the navigation module 154 receives a sequence of frames, several of which may be captured while the display is in transition: a page is loading, a dialog is animating, a camera image is blurred, or the content of interest has momentarily scrolled away. For such a frame the first model 172 correctly returns a navigation record 1304 that identifies neither an instruction nor an observation, because there is nothing yet to instruct or observe. Treating that record as an unusable model output and re-submitting the frame to the stronger model 174, as paragraph [0042] does for a one-off read, is wrong in the loop: it spends the costlier model on display noise, it switches models on a signal that says nothing about the model, it raises a false incident, and the next frame would in most cases have recovered on its own. The tolerance 1300 makes escalation a function of persistence across frames rather than of one frame's usability.

[0109] For each frame 1302 captured in the watch loop and redacted on the device, the navigation module 154 obtains the navigation record 1304 from the first model 172. At decision 1306 the record is classified as readable when it identifies an instruction or an observation, and as unreadable when it identifies neither. For a readable record, at 1308 a per-session count of consecutive unreadable records is reset to zero and the record is applied as described with reference to FIG. 2: steps shown satisfied are marked, the current step advances or a corrective instruction is given, and flags are surfaced. For an unreadable record, at 1310 the count is incremented and persisted with the session. At decision 1312 the count is compared with a tolerance threshold (in one embodiment two). While the count is below the threshold, at 1314 the stronger model 174 is withheld: the redacted frame is not re-submitted, the current step and the instruction already presented remain unchanged, no escalation event and no operator incident is raised, and the frame is nonetheless recorded in the transmission audit of FIG. 5 like every other frame, so that the withheld escalation is visible in the audit trail and is not silent. When the count has reached the threshold, at 1316 the stronger model 174 is permitted: the next captured frame whose first-model record is unreadable is re-submitted, with the plan, to the stronger model 174 for that call, the escalation is recorded as an event visible to the user as in paragraph [0042], and the count continues until a readable record resets it. A read that the user requests explicitly as a deep read, at 1318, is escalated on an unreadable first-model record regardless of the count, because the user has asked for the stronger reading of this particular frame. A one-off read outside the loop retains the immediate escalation of paragraph [0042].

[0110] The count is a consecutive streak: it is reset by any readable record, so three unreadable frames separated by readable ones never escalate, while two unreadable frames in a row do. In an alternative embodiment the persistence test is a sliding window over the most recent frames of the session, under which escalation is permitted when at least a first number of the last second number of frames (for example two of the last five) produced unreadable records, the window advancing with each frame; this embodiment tolerates an isolated unreadable frame equally but also catches a display that alternates between readable and unreadable states. In either embodiment the tolerance threshold is a named constant, and in some embodiments it scales with the guidance intensity selected for the session. The tolerance applies only to the readability signal; an error raised by the first model, as opposed to an empty but well-formed record, continues to escalate immediately as in paragraph [0042], and a successful response that contains no content at all is classified as a retriable failure of the model rather than as an unreadable frame and is handled by the reliability ladder of paragraph [0087] within the same credential, without transmitting the redacted frame under any other credential.

[0111] The technical effect of the tolerance is specific to screen-sampled guidance of a human performer. An autonomous agent that acts on each frame cannot tolerate a blank reading, because it must decide an action for that frame; a guidance system that waits for a human to act can, because the human's action is already under way and the next frame is the oracle. Withholding the stronger model within the tolerance therefore reduces cost and false incidents without reducing the guidance the user receives, since within the tolerance the correct guidance is in every case the instruction already presented.

[0112] The project engine of FIG. 10 to FIG. 12 and the tolerance of FIG. 13 may each be used with the loop of FIG. 2 and with the other embodiments described, or independently of them, as the claims define; in particular the breakdown gate 1100, the injection flow 1200 and the project report generator 1036 operate on the project map 1006 and its guided sessions however those sessions are presented, and the tolerance 1300 applies to any embodiment in which frames are sampled repeatedly while the user performs an instructed action.
