## FIELD OF THE INVENTION

[0001] The present disclosure relates to computer-implemented assistance systems and, more particularly, to systems and methods that observe a user's display while the user operates an arbitrary target application, generate step-by-step instructions that the user performs, verify from subsequently captured display content that each step was actually performed before advancing, and protect sensitive information by redacting or tokenizing it on the user's device before any content is transmitted to a remote machine-learning model, under a policy governed per organization.

## BACKGROUND OF THE INVENTION

[0002] Users of software routinely need to accomplish tasks in applications they do not fully understand: configuring a cloud resource, reconciling a spreadsheet, filling a regulated form, running a sequence of terminal commands, or navigating an enterprise system. Conventional help takes the form of static documentation, pre-authored "walkthroughs" injected into a particular web application, or chat assistants that answer questions without seeing what the user sees. These approaches either do not apply to arbitrary applications, cannot tell where the user actually is, or cannot tell whether an instruction was carried out correctly.

[0003] A more recent class of systems — robotic process automation and so-called agentic assistants — captures the user interface and then performs actions on the user's behalf by injecting clicks and keystrokes. Such systems are frequently unacceptable in regulated or security-sensitive environments because an autonomous component with write access to the user's systems can make unintended or malicious changes, cannot easily be audited, and shifts accountability away from the human operator. They are also brittle when the predicted action is wrong, since the system itself executes the error.

[0004] Separately, any assistant that transmits a screenshot or a prompt to a remotely hosted model exposes whatever is on screen or in the prompt — personal data, protected health information, credentials, keys, card and account numbers, internal host names — to the model provider. Known mitigations either mask fields within the assistant's own application (and thus cannot protect content shown by a third-party application), remove sensitive data irreversibly so that the answer loses the needed values, or perform masking at an organizational gateway or server after the data has already left the user's device. Organizations further lack a mechanism to govern, per tenant, what their members' devices may transmit and whether screen captures are retained at all, in a way that the member cannot weaken.

[0005] There is therefore a need for a guidance system that works on any application, that confirms from the screen that each instructed step actually happened before moving on, that never acts on the user's behalf, that strips or tokenizes sensitive data on the device before transmission while still returning a complete answer to the user, and that lets an organization govern data egress and screenshot retention for its members with enforcement on the device.

## SUMMARY OF THE INVENTION

[0006] This summary introduces a selection of concepts in simplified form that are further described in the Detailed Description. It is not intended to identify key or essential features of the claimed subject matter.

[0007] In one aspect, a computer-implemented method is provided in which a guidance client executing on a user device receives a user-stated goal to be accomplished in a target application; obtains, from a machine-learning model, an ordered plan of steps, each step comprising an instruction and a visible-when-done condition describing display content that will be present when the step has been performed; repeatedly captures frames of the device display; redacts each frame on the device by recognizing text within the frame and masking regions containing text identified as sensitive by a policy engine, before the frame is transmitted; transmits the redacted frame together with the plan to a model having image-understanding capability; receives a navigation record identifying which steps are visibly completed, which single step is current, one screen-specific instruction for that step, an observation, and any flag; presents the instruction to the user without injecting any input event into the target application; and advances the current step only when a subsequently captured frame shows the visible-when-done condition satisfied, otherwise presenting a corrective instruction.

[0008] In another aspect, a system comprises a guidance client and a guidance server. The guidance client includes a capture module, an on-device redaction engine, a token map held only in volatile memory of the user device, a policy-enforcement module, and a local rehydration module. Sensitive values in outbound text are replaced, according to the policy, with stable typed placeholder tokens whose mapping to real values never leaves the device; the remote model operates on placeholders; and the response, including streamed partial responses, is rehydrated locally. A placeholder absent from the response is left in place and flagged, never guessed.

[0009] In another aspect, a non-transitory computer-readable medium stores instructions implementing a tenant-governed egress policy object comprising per-category actions, block words, custom patterns, a mode selecting redaction or tokenization, a screenshot-evidence retention setting, a retention window, and armed/locked state; the policy is distributed to member devices and enforced there before any transmission, re-applied by the server as defense in depth, and cannot be weakened by a member; an append-only audit log records, for each transmission, counts of what was removed rather than the values.

[0010] Further aspects include: capturing, as evidence for a step, the already-redacted frame at the moment the step is first verified, so that no additional content leaves the device; a no-install floating overlay implemented with a browser-native picture-in-picture document window with a pop-out fallback; a desktop overlay configured for click-through, adjustable opacity and content protection such that the overlay is excluded from the device's own capture and from screen sharing; escalation from a fast model to a stronger model when the navigation record is unusable; a deterministic security gate that flags destructive commands and known-vulnerable dependency versions in any command or code handed to the user; and a session report containing confirmed steps with timestamps and the redacted evidence frames, encrypted at rest.

## DETAILED DESCRIPTION OF THE INVENTION

### Overview and terminology

[0016] The following description refers to the accompanying drawings. Reference numerals are consistent across figures. The term **target application 190** refers to any software with which the user is interacting on the user device, including native desktop applications, web applications in a browser, terminals, and, in a mobile embodiment, a physical screen viewed through a camera. The target application is not modified, instrumented, or required to cooperate. The term **guidance client 120** refers to the software component of the present disclosure executing on the user device 110. The term **frame** refers to a captured image of some or all of the display 112 (or a camera image of a screen). The term **navigation record** refers to the structured output described with reference to FIG. 2. The term **read-only** means that the guidance client 120 is configured so that it does not inject pointer events, keyboard events, commands, form submissions, messages, or any other input into the target application 190 or the operating system on the user's behalf; every state change in the target application is performed by the human user.

### System architecture (FIG. 1)

[0017] Referring to FIG. 1, a system 100 comprises a user device 110 having a display 112, an input device 116 (keyboard, pointer, touch), a screen-capture interface 114 provided by the operating system or browser (for example, a display-media API in a browser, a desktop capturer in a desktop shell, or a camera on a mobile device), and a target application 190 rendered on the display 112.

[0018] The guidance client 120 executes on the user device 110 and comprises: a capture module 122 that obtains frames from the screen-capture interface 114 at a configurable rate (for example about one frame per second during continuous watching, with a change detector so that only frames that differ materially from the previous frame are processed); an on-device redaction engine 124 described with reference to FIG. 3; a token map 126 stored only in volatile memory of the user device 110; a policy-enforcement module 128 that holds the effective egress policy for the user (FIG. 5) and gates every outbound transmission; a local rehydration module 130 that substitutes real values back into model responses; and a presentation layer 132 that displays instructions, flags and observations to the user. In one embodiment the presentation layer 132 is a floating overlay 134 described below.

[0019] The guidance client 120 communicates over a network 140 with a guidance server 150. The guidance server 150 comprises a planning module 152, a navigation/verification module 154, a server-side policy re-enforcement module 155 that re-applies the same policy engine as a second line of defense, an append-only audit log 156, an evidence store 158 holding redacted milestone frames and reports encrypted at rest (for example AES-256-GCM with a managed key), a policy store 160 holding egress policy objects per tenant and per user, and a security gate 162 that deterministically checks commands and code before they are shown to the user.

[0020] The guidance server 150 invokes one or more model services 170, comprising at least a first machine-learning model 172 having image-understanding capability and relatively low latency (a "fast vision model") used for per-frame navigation, and optionally a second, stronger model 174 used for planning and for escalation when the first model's output is unusable. The model services 170 may be hosted by a third party and accessed with credentials belonging to the operator of the guidance server or, in a bring-your-own-key embodiment, with credentials belonging to the tenant. A tenant administration console 180 allows an administrator of an organization (a tenant) to author and arm the egress policy described with reference to FIG. 5 and to retrieve session reports and audit logs for members of that tenant only.

[0021] It will be understood that the division of functions between the guidance client 120 and guidance server 150 may vary. In particular, the redaction engine 124, token map 126, policy-enforcement module 128 and rehydration module 130 are located on the user device 110 in every embodiment, because their purpose is to ensure that raw sensitive values never leave the device. The planning module 152 and navigation module 154 may alternatively execute on the device when a suitable model is available locally.

### Plan generation with visible-when-done conditions

[0022] When a user states a goal (for example, "create a VPC with a public and a private subnet in region X," "reconcile this bank statement against the ledger," or "configure single sign-on for this tenant"), the guidance client 120 transmits the goal — after on-device cleaning by the policy-enforcement module 128 — optionally with an initial redacted frame, to the planning module 152. The planning module 152 may first conduct a short scoping interview (a small set of goal-specific questions whose answers are folded into the plan), may retrieve current reference material (for example by reading a link named in the goal), and may incorporate user-provided reference documents that, in a desktop embodiment, are extracted and governed entirely on the device and used for that plan only.

[0023] The planning module 152 prompts the model 174 to return an ordered list of steps, each step being a data record comprising: `text` (a short action name), `validate` (a **visible-when-done condition** — the specific display content that will be visible once the step is truly done), optionally `url` (an official page to open), `commands` (an array of exact commands to type, ready to copy, with real values filled in), and `code` (a file path and exact file content). The plan is grounded, per discipline, by a method anchor selected from a catalog of canonical methodologies keyed to the goal's field, so that steps follow the standard professional method for that field.

[0024] Each returned step is passed through the security gate 162, which (a) deterministically matches commands and code against a catalog of destructive patterns (for example, recursive deletion, dropping a database, force-pushing over history, infrastructure teardown, disk formatting) and sets a `destructive` flag with a human-readable reason so that the presentation layer 132 hides such a step behind an explicit acknowledgment; and (b) checks dependency versions named in code against a vulnerability database and annotates known-vulnerable versions with the safe fix. When the vulnerability database is unreachable the gate reports that fact rather than silently passing.

### The observe–instruct–verify–correct–advance loop (FIG. 2)

[0025] Referring to FIG. 2, loop 200 begins at step 202 with receipt of the goal and at step 204 with generation of the plan as described above. At step 206 the capture module 122 captures a frame. At step 208 the redaction engine 124 produces a redacted frame on the device (FIG. 3). At step 210 the guidance client 120 transmits the redacted frame together with the cleaned goal and the entire checklist (every step with its current status and its visible-when-done condition) to the navigation module 154.

[0026] At step 212 the navigation module 154 prompts the model 172 with the frame and checklist and instructs it to read the screen and determine where the user **actually** is — not where the list assumes — recognizing that the user may have finished several steps, skipped one, done them out of order, or be on a screen the plan did not foresee. The model is required to return a **navigation record** consisting of: `completed` — the step numbers the frame shows are genuinely finished (only steps whose completion can actually be seen); `current` — the one step the user should do next, judged from the frame; `guidance` — the next action written for this exact screen, naming the real visible control (for example, "Click the orange Create VPC button, top right" or "In the IPv4 CIDR field type 10.0.0.0/16") or giving the exact command or code to type, limited to one micro-action; `observation` — one sentence stating what is on screen; `flag` — the specific problem and its fix if something is wrong or risky (wrong value, wrong place, an error message, a paid option where a free one was wanted), otherwise empty; and `done` — true only when the whole goal is complete on screen. In one embodiment the record is a JSON object `{"completed":[...],"current":n,"guidance":"...","observation":"...","flag":"...","done":bool}`; step numbers are one-based in the prompt and converted and bounds-checked by the server.

[0027] At decision 214 the navigation module 154 applies the gating rule: the current step may advance only if the frame shows the visible-when-done condition of the previously instructed step (or any later step) satisfied. If so, at step 216 the server marks those steps completed, records the time of confirmation, and — if evidence retention is enabled by the governing policy — stores the already-redacted frame as that step's milestone evidence in the evidence store 158, exactly once per step. If not, at step 218 the guidance field carries the exact corrective micro-action; where an error is visible, the model reads the error and gives the exact fix; where the model cannot see what it needs (output scrolled off, a dialog covering it, a blurry camera), the guidance asks the user to make it visible ("Scroll down so I can see the command output"). At step 220, any flag is surfaced prominently (and cleared automatically when a later frame shows the user back on track).

[0028] The loop additionally implements two rules that make it robust to real-world drift. First, **proactive prerequisite insertion**: if the current step cannot be done yet because something earlier is missing on screen (the project, scenario, sheet or table it needs does not exist; a required button is absent or disabled because setup is incomplete), the model does not repeat the blocked instruction and does not wait for the user to get stuck; it makes the missing prerequisite the guidance, sets `current` to it, and states in the observation what was missing. Second, **UI drift handling**: because the target application may have changed since the plan was generated, if the exact control named in a step is not visible, the model is instructed never to tell the user to click something that is not there and never to repeat a stale instruction; it identifies the control that now performs the same function (new label, different tab or menu, moved) and guides to that, noting the difference, and only if no equivalent is visible does it say so and direct the user to research the current interface.

[0029] At step 222 the presentation layer 132 displays the guidance (and the observation and any flag). At step 224 — shown outside the system boundary — the **human user performs the action** in the target application 190 using the input device 116. The guidance client 120 contains no code path that injects an input event into the target application; every state transition of the target application is the user's own. At decision 226, if `done` is true, the loop ends at step 228 with generation of the session report; otherwise the loop returns to step 206 for the next frame. The subsequently captured frame is thus the oracle by which the system verifies that the instructed action was performed and succeeded.

[0030] **Model escalation.** The navigation module 154 evaluates whether the first model's output is usable (i.e., contains at least a guidance string, a non-empty completed list, a current index, an observation, or done = true). If the output is unusable, the same frame is re-submitted to the stronger model 174 ("just-in-time deep pass"); the user may also request a deep pass explicitly. The escalation, and any failure of the stronger model, is recorded as a visible event so that the user is never silently served a weaker result than the one the operator configured. The actual model identity is kept in the server audit and operator incident log and is not shown to end users.

[0031] **Periodic self-audit.** Independently of the per-frame navigation, a less frequent step-back check submits the goal, the checklist, the recent action history and the current redacted frame and asks only whether the work is still heading at the goal or has drifted or stalled (the same step failing repeatedly, the screen having moved onto something unrelated, guidance no longer matching the screen). It returns `onTrack`, a one-sentence `steer`, and a `replan` suggestion. It never changes the plan itself; re-planning is initiated by the user and may preserve already-confirmed steps.

[0032] **On-demand channels.** In addition to the continuous loop, the user may ask a question about the current screen ("what is this / what do I do here"), request the actual result of a task (a number, table, query or code) accompanied by a confidence indicator, a statement of how it was obtained and how to verify it, or request a composed document. All of these channels pass through the same policy-enforcement module 128 before transmission. In a further embodiment, a spreadsheet computation is performed entirely on the device: the file is parsed locally, only a description of the request, the column schema and the row count are transmitted, a computation specification is returned, and the specification is executed locally over the full data so that the rows never leave the device.

### On-device redaction, tokenization and local reconstruction (FIG. 3)

[0033] Referring to FIG. 3, pipeline 300 is executed on the user device 110 by the redaction engine 124 and the policy-enforcement module 128. Two kinds of outbound content enter the pipeline: outbound text 302 (the goal, questions, pasted sources, document text) and outbound frames 304.

[0034] A detector 306 identifies sensitive spans using a catalog of rules. In one embodiment the rules include: private-key blocks; API keys, tokens and credentials by provider-specific patterns and by label (a value adjacent to a label such as password, secret, api key, access token, client secret); URLs embedding credentials; government and financial identifiers including social-security/social-insurance numbers, card numbers validated by checksum (so that version strings are not falsely matched), IBANs, bank account and routing numbers; email addresses and phone numbers; IPv4 and IPv6 addresses (version strings guarded) and private or internal host names; and labelled health and personal record fields such as date of birth, medical record number, patient, member, policy and account numbers, driver-license, passport and tax identifiers, street addresses and postal codes. The detector deliberately preserves public product domains, file paths, commands and version numbers so that guidance quality is retained. The same detector code executes on the device and on the server (a single implementation), so there is no weaker path.

[0035] A policy 308 (the effective egress policy for the user, see FIG. 5) supplies, per category (secrets, PHI, PII, intellectual property, host, email, phone, card, SSN, IBAN, and custom), an action selected from **send**, **redact** (irreversibly replace with a typed tag such as `[EMAIL]`, `[IP]`, `[REDACTED]`), **withhold**, or **tokenize** (reversibly replace); a list of **block words** (exact words or phrases, such as a project code name or client name, that are always removed and never reversible); and **custom patterns** with their own actions. An action router 310 applies the policy to each detected span.

[0036] For a span whose action is tokenize, a token generator 312 produces a **stable, typed placeholder token**, for example `[[EMAIL_1]]`, `[[IP_2]]`, `[[CARD_3]]`, `[[SECRET_4]]`, `[[HOST_5]]`. The token format is chosen to be distinctive and unambiguous so that a language model preserves it verbatim, and it carries a safe type hint so that the model still reasons correctly about the kind of value (an address, an identifier, a secret) without seeing it. The same real value is always mapped to the same token within a session (a value-to-token index is maintained), so references stay coherent across turns. The token-to-value mapping is written to the token map 126 (step 314), which resides only in volatile memory of the user device, is never included in any request, is never written to any server log, and is discarded when the session ends. In one embodiment only "whole-match" categories (where the matched text is exactly the value, such as an email address or an IP) are reversibly tokenized, while labelled fields (a value embedded in a label) are redacted irreversibly.

[0037] For outbound frames 304, the redaction engine 124 performs on-device optical character recognition 316 of the frame (for example using a recognition engine loaded into the browser or desktop shell, with the engine pre-warmed when a protected session begins so that the first frame is not delayed). For each recognized text line, the recognized text is passed through the **same** detector 306 and policy 308 used for typed text, including the tenant's block words and custom patterns. If any sensitive span is found in a line, a line-mask step 318 paints an opaque rectangle over the entire line's bounding box (with a small margin) on a canvas copy of the frame; masking the whole line is more robust than attempting to locate the individual word and is tolerant of values split across words. The canvas is re-encoded (for example as a compressed JPEG) to produce the redacted frame 320. If nothing sensitive was found the original frame is used. If the recognition engine cannot run (for example it failed to load), a strict fail-safe produces a heavily downscaled copy of the frame so that fine text is not legible, rather than transmitting the full-resolution frame; this is reported honestly as a best-effort backstop rather than a guarantee, and the user retains control of what is on screen and which display is shared.

[0038] The tokenized or redacted text 322 and the redacted frame 320 are then transmitted (324) to the guidance server 150 and on to the remote model 326. Before transmission the user is shown a short summary of what was removed on the device (for example, "Stripped on your device before sending: 2 emails, 1 IP address"), and nothing is ever silently dropped.

[0039] The model's response 328 contains placeholders where it refers to tokenized values. The local rehydration module 130 performs rehydration 330 by substituting each token in the token map 126 with its real value. Rehydration is applied to every string in the response structure (deep-walking objects and arrays) and, in a streaming embodiment, to each partial chunk as it arrives so the user reads a complete answer in real time. A missing-token handler 332 deals with the case where a token is absent, garbled, or altered in the response: the placeholder is left in place and the answer is flagged as incomplete at that point; the system never guesses or fabricates a value. The displayed answer 334 therefore names the exact real values (for example a specific patient record number) although neither the guidance server nor the model ever received them. An audit entry 336 records the call, whether protection was on, the counts of what was removed by category, whether a frame was sent, and the protected text that actually left the device — the entry contains placeholders and tags, never raw values.

[0040] **Defense in depth.** The guidance server 150 applies the identical policy engine again to inbound text (module 155) so that a control is enforced even if the first layer is bypassed. Text that is persisted for later re-use (for example a saved playbook or a knowledge-base learning) is always redacted rather than tokenized, because stored text is shared and never rehydrated; the server applies a mandatory scrub floor on write and the same policy on injection into any later prompt.

### One guided step end to end (FIG. 4)

[0041] FIG. 4 shows participants: the human user 402, the target application 404 (190), the guidance client 406 (120), the guidance server 408 (150), and the model service 410 (170). At 412 the user states the goal; at 414 the client cleans it on device (pipeline 300) and sends it; at 416 the server obtains the plan with visible-when-done conditions from the model and returns it (418). The loop then proceeds: at 420 the client captures a frame of the target application; at 422 it redacts the frame on device; at 424 it sends the redacted frame with the checklist; at 426 the server submits them to the model and at 428 receives the navigation record; at 430 the server applies the gating rule and, if evidence is enabled, stores the redacted frame for any newly confirmed step; at 432 the server returns the navigation record (status working / wrong / done) to the client; at 434 the client presents the one micro-action, the observation and any flag. At 436 — a message from the user to the target application that does **not** pass through the client — the user performs the action. At 438 the target application's display changes. At 440 the client captures the next frame, and the cycle repeats from 422. The only arrow that changes the state of the target application originates from the human user.

### Tenant-governed egress and screenshot-retention governance (FIG. 5)

[0042] Referring to FIG. 5, arrangement 500 comprises a tenant administrator 502 who, through a policy editor 504 in the administration console 180 (optionally a guided wizard seeded from compliance-framework presets such as those mapping to healthcare, payment-card, or general data-protection regimes, and from regional regimes), authors a **policy object 506**. The policy object comprises: per-category actions 508 (send / redact / withhold / tokenize); block words 510; a mode 512 selecting redaction or tokenization; a **screenshot-evidence setting 514** controlling whether redacted milestone frames are retained in session reports and logs for the tenant's members at all; a retention window 516 after which sessions, their evidence frames and their audit logs are deleted together; and an armed/locked state 518. Custom patterns with their own actions are also part of the object. The object carries a version number and the identity of who last changed it.

[0043] Arming the policy makes it the enforced criteria for every member of the tenant. Locking the policy requires an explicit unlock, which in one embodiment requires re-authentication by a platform-level administrator and creates an audit entry, before any change is accepted; an attempt to modify a locked policy is refused. Scope resolution 520 determines the effective policy for a user: a member of a tenant receives the tenant's armed policy and cannot edit, weaken, or opt out of it (the self-service policy controls are denied to members); an individual not belonging to any tenant may manage their own policy; a platform administrator may set and lock any policy.

[0044] The effective policy is distributed (522) to each member's guidance client 120, where the policy-enforcement module 128 applies it on the device, before transmission, to typed text and to screen frames alike (pipeline 300). The guidance server 150 re-applies the identical policy on receipt (524) as a second line of defense. The screenshot-evidence setting 514 gates whether the server stores the redacted frame at step 216 of FIG. 2 (evidence store 526 / 158); when disabled, no frame is retained anywhere and the report contains the confirmed steps and timestamps without exhibits. A retention sweep 528 runs periodically and deletes sessions older than the retention window together with their evidence frames and audit logs. A transmission audit 530 (log 156) records, per call, the policy version in force, the mode, and the counts of what was withheld, tokenized, or blocked — never the values — together with whether a frame was sent and what the assistant read from the screen. An administrator may retrieve any member session's report and audit log, in progress or finished, scoped strictly to their own tenant (532); a member-level alert (who, what categories and counts, which task, when — never the values) is raised to the tenant administrator when a member enters sensitive data that was redacted on device, and may be relayed to the tenant's security-event tooling.

### Presentation: floating overlay, desktop shell and mobile variant

[0045] In a no-install browser embodiment, the guidance client 120 runs as a web application and the floating overlay 134 is realized with a browser-native picture-in-picture document window (a small always-on-top window containing live document content rather than video) so that the current step, the exact command with a copy control, the observation and any flag float over whatever application the user is working in, including on locked-down machines where installing software or browser extensions is not permitted. Where the browser does not support such a window, the client falls back to a pop-out window, and where pop-ups are blocked, to in-page presentation, in each case telling the user why. Copy controls are implemented so that they work both in the main page and in the floating window. The display is read through the browser's display-media capture API with the user choosing what to share.

[0046] In a desktop embodiment, a desktop shell hosts the client in two modes: a planning mode (a normal, resizable window) and a guiding mode in which the window becomes a compact always-on-top overlay with adjustable opacity and a click-through mode in which pointer events pass to the application beneath so the user can work underneath the guidance. The shell answers the display-media request with the chosen monitor (remembered across sessions on multi-monitor machines) and applies **content protection** so that the overlay, and the monitor picker, are excluded from the capture (avoiding a feedback loop in which the overlay's own text is read as screen content) and from screen sharing and recording by conferencing software; the protection is user-toggleable. A compact companion card may show the current step while the main window is hidden, and a full-screen guide may be shown on a second monitor with a reader-controlled font size. Reference documents are extracted on the device (including images and scanned pages) and used only for the current plan. The shell has no capability to drive the machine.

[0047] In a mobile embodiment, where display capture is unavailable, the frame source is a camera image of a physical screen or a chosen photograph, downscaled to the same budget as a live frame and fed into the same plan, ask and navigate flows, with the same on-device pipeline 300.

### Session record and auditability

[0048] At the end of a session (or on demand, in progress), the guidance server 150 produces a session report comprising: the goal; every planned step in order with its status; for each **confirmed** step only, the timestamp of confirmation, the exact commands and code handed over, and — where permitted by setting 514 — the redacted milestone frame as an exhibit; steps not performed are listed by name and status only, so detail never leaks for steps the user did not perform. The report and the evidence frames are encrypted at rest. A downloadable, append-only, human-readable audit log lists each transmission with its timestamp, purpose, protection state, counts removed, whether a frame was sent, and the protected text that left. Both report and log carry an authenticity seal (a digest and keyed message-authentication code verifiable at a public endpoint) so that any party can confirm the record was issued unchanged. Deleting a session removes the record, its evidence frames and its audit log together.

[0049] A third party may validate the on-device protection independently of the server by observing the request bodies leaving their own machine with developer tooling or a local proxy while running a session containing known test values, and confirming that only placeholders or tags are present; the server log then corroborates what was observed. This verification path exists because the primary control runs on the device, not on the server.

### Model routing and reliability

[0050] The guidance server 150 routes to the highest-ranked model reachable with the credentials in effect for the user (the operator's platform credentials or the tenant's own credentials), with a reliability ladder: a retired or rate-limited model is replaced by another current model on the same credentials, then (in platform-credential mode only) by the next provider; a tenant's own credentials are never silently replaced by the operator's. Every switch is logged as an operator incident and the user is shown a neutral notice that a switch occurred rather than a raw failure; the user is never shown the model name.

### Implementation notes

[0051] In one implementation, the guidance client is a single-page web application; the guidance server is an HTTP service with JSON persistence using atomic writes; the desktop shell is a cross-platform desktop wrapper loading the same web client; the on-device OCR is a WebAssembly recognition engine executed in a worker; the frame rate during watching is about one frame per second at reduced resolution for cost, with full resolution for one-off reads; the navigation prompt requests JSON only, and the server extracts, bounds-checks and sanitizes the returned fields (including an output scrubber that removes model-identifying or stylistic artefacts) before returning them to the client. These details are illustrative; other languages, runtimes, recognition engines, and models may be used.

## ABSTRACT OF THE DISCLOSURE

A guidance client on a user device captures frames of the display while the user operates any target application, redacts each frame on the device by recognizing text and masking lines that a policy engine identifies as sensitive, and transmits the redacted frame with an ordered plan whose steps each carry a visible-when-done condition. A vision-capable model returns a navigation record identifying visibly completed steps, the single current step, one screen-specific instruction, an observation and any flag. The client presents the instruction without injecting input into the target application; the human performs every action, and the plan advances only when a later frame shows the expected result, otherwise a corrective instruction is given. Outbound text is reversibly tokenized with placeholders whose mapping stays only in device memory, and responses are rehydrated locally. A per-tenant egress policy, including screenshot-evidence retention, is enforced on-device and audited by counts rather than values.
